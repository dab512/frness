# Правила работы в FRNESS

Общение с пользователем — на русском. Это самостоятельный GitHub-проект; предметные решения описаны в specs/fractal-harness.

## Порядок реализации

1. Прочитать specs/fractal-harness/README.md, ARCHITECTURE.md, CONTRACTS.md и HANDOFF.md.
2. Выбрать первый незавершённый этап из plan.json, зависимости которого завершены.
3. Выполнить его точный AT-сценарий из atomic-gates.json. plan.tests задаёт полную трассировку, а не ранний gate недоступных компонентов.
4. Проверить типы, линтер, тесты и локальный пользовательский сценарий доступного этапа.
5. Сохранить фактический результат и свидетельства в implementation-status.json.

## Обязательные ограничения

- Host не знает о Request, Invocation, Session, Project или агентских статусах. Они определяются стандартными плагинами.
- Публичные контракты не менять ради удобства реализации. Противоречие сначала исправляется в спецификации с отдельным объяснением.
- Совместимость номинальная: точный ContractRef; ссылки и версии закреплены сборкой.
- Нельзя повторять неизвестный внешний эффект без предусмотренной стратегии.
- Replay не обращается к живым моделям, инструментам и рабочим данным.
- Закрытие UI не отменяет исполнение и не удаляет данные.
- Каждый плагин поддерживает generation-safe hot reload по HOT-RELOAD.md; системные пакеты тоже. Не сбрасывать данные или pinned invocations ради reload.
- Тесты не подгонять под код; skip, xfail и заглушки успешного результата не закрывают этап.
- Не добавлять атрибуцию AI-инструмента в commit message.
- Перед commit/push проверять текущую ветку, diff и результаты проверок. Не перезаписывать историю удалённого репозитория.

Публикация изменений выполняется в пределах текущего поручения пользователя. Разрешение на первый push спецификации получено в разговоре; повторное подтверждение не требуется.
