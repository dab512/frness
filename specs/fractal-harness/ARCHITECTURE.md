# Архитектура фрактального харнеса

## Обязательные требования

- REQ-01: исходная конфигурация выполняет один LLM-вызов и показывает вопрос–ответ.
- REQ-02: метамодель описывает Type, Contract, Implementation, Instance, Slot, Binding; её определения также являются данными.
- REQ-03: Request, Invocation, Effect, Session, Project, View, Tab, History, Fork и Memory определяются пакетами плагинов, не кодом host.
- REQ-04: плагин владеет схемой, операциями, миграциями и областью своих данных; backend хранения подключается по контракту.
- REQ-05: плагин может объявлять новые слоты, принимающие чужие реализации по точному контракту.
- REQ-06: UI расширяется тем же способом, включая контейнеры, действия, историю, ветки и проекты.
- REQ-07: сборка, версии, состояния и эффекты позволяют воспроизведение, восстановление и управляемое ветвление.
- REQ-08: предметные операции доступны через общий API из UI, CLI и автоматизации.
- REQ-09: отмена, права, бюджеты и проверка результата работают на вложенных компонентах.
- REQ-10: установка, обновление, диагностика и резервное копирование имеют воспроизводимые процедуры.
- REQ-11: каждый плагин, включая системные, поддерживает hot reload без перезапуска host/web shell, с сохранением данных и откатом неудачного candidate.

## Решение D01 — небольшой технический host

Host знает JSON-значения, непрозрачные ссылки, пакет с digest, технический ABI, выдачу capabilities, загрузку экспортов и передачу вызовов. Начальные метаописания поставляются закреплённым bootstrap bundle. Host сначала проверяет его конечной встроенной bootstrap-схемой, затем стандартный валидатор проверяет те же определения через загруженную метамодель.

Самоописание не означает изменение ABI через редактирование записи. Новое значение декларации получает смысл только при наличии совместимой реализации интерпретатора.

В packages/host запрещены импорты стандартных предметных плагинов, колонки session_id/project_id/request_id и ветвления по состояниям агента. Технические ошибки ABI разрешены. Долговечное исполнение реализует обязательный для durable-профиля плагин execution; host не знает, что такое «задача принята».

## Решение D02 — определения и экземпляры

Package — поставляемый артефакт. Definition — неизменяемое описание внутри его версии. Instance — установленный компонент с собственным состоянием. Object — сохраняемые данные. Invocation — объект конкретного исполнения, определённый execution-плагином. Mount — объект отображения, определённый UI-плагином.

Ссылки на определения содержат packageId, точную packageVersion, digest и name. Установить другие байты под той же парой packageId/version нельзя. Сборка закрепляет точные ссылки; latest, диапазоны версий и зависимость от порядка установки в исполняемой сборке запрещены.

Идентификатор экземпляра не выводится из его пути. Перенос узла не меняет namespace состояния. У двух экземпляров одной реализации разные namespaces. У двух mounts одного объекта одинаковый ObjectRef и разные mountId.

## Решение D03 — конечное дерево композиции

Каждый экземпляр имеет не более одного владельца. Сборка содержит один корень и все остальные экземпляры достижимы по owning bindings. Цикл, два родителя и недостижимый экземпляр — ошибка сборки. Повторный вызов ребёнка не создаёт ребро назад.

Ссылки на данные и общие ресурсы образуют отдельный граф. Они не передают владение и не создают права. Один физический store может обслуживать разные namespaces.

Слот имеет single/ordered/keyed форму и min/max кардинальность. Порядок явный; ключи и позиции уникальны. Вызовы, последовательность, параллелизм и fallback определяет логика родителя. Linker не придумывает эти правила.

Совместимость в v1 номинальная: точное равенство ContractRef. Похожих JSON-схем недостаточно. Для другой версии нужен явный adapter-плагин. Семантическая заменимость проверяется conformance suite контракта; автоматически доказать её для произвольного кода не обещаем.

## Решение D04 — общий transactional store и собственные данные

Плагин определяет схемы и миграции. Repository capability ограничивает его namespace и scope. Durable-профиль первой версии требует один SQLite backend с поддержкой атомарной транзакции нескольких разрешённых namespaces, WAL и foreign keys. JSON-объекты хранятся в generic records/revisions; предметные колонки в storage driver не нужны.

Store реализуется самостоятельным плагином. In-memory adapter применяется в unit-тестах и явно недолговечных сборках. Другой adapter разрешён, если проходит тот же storage conformance suite. Durable-сборка с backend без требуемых атомарных гарантий отклоняется до старта.

Внешний API, файловая система инструмента и другая БД считаются внешними эффектами. Они не участвуют в локальной SQLite-транзакции автоматически. Плагин не должен обходить переданную storage capability для данных, объявленных долговечными.

## Решение D05 — доверенные плагины и границы полномочий

Первая версия исполняет локально установленные доверенные плагины. Ограниченные SDK capabilities защищают от ошибок композиции, но процесс Node с произвольным кодом не является sandbox. Изоляцию недоверенного кода нельзя отмечать готовой.

Право определяется контекстом вызова, не полем запроса. Дочерний компонент получает пересечение разрешений предков и явно выданных прав. Контракт может сузить набор разрешённых эффектов. API проверяет право заново, даже если UI ранее показал доступную кнопку.

Новый внешний канал или секрет не добавляется в доступы только из-за установки плагина. Секрет передаётся адаптеру через credential capability; сохраняемые запросы содержат ссылку, а не токен.

## Решение D06 — durable execution как стандартный плагин

Execution определяет Request, Invocation, Effect, Attempt, Reservation, InboxEvent и Checkpoint через метамодель. Reducer детерминирован: state + input event → next state + commands. Сетевые действия, случайность и актуальное время приходят через зарегистрированные эффекты.

RUNTIME.md задаёт обязательные автоматы, транзакции и crash points. Replay работает в отдельном scratch store с записанными ответами. Resume сохраняет идентичность и закреплённые версии. Fork создаёт новые идентификаторы продолжения и не повторяет исторические внешние действия.

Технический успех Invocation не означает правильный ответ. Плагин agent принимает кандидат только по обязательным verifier-результатам, привязанным к digest кандидата и версиям проверок.

## Решение D07 — версии и обновления

Установка: stage → проверить digest/зависимости/схемы → собрать клиентский артефакт → выполнить conformance → активировать новую сборку атомарно. Ошибка до activation оставляет прежнюю активную сборку.

Новый запуск использует новую сборку; начатый сохраняет старую. Live migration активного invocation в v1 отсутствует. Старые пакеты, определения и снимки сохраняются, пока на них существуют ссылки. Disable запрещает новые вызовы через текущую сборку; активные исполнения завершаются по своим закреплённым зависимостям. Unmount закрывает только представление.

Hot reload обязателен для каждого пакета по HOT-RELOAD.md: capture → candidate restore/ready → generation CAS/publication → drain/dispose. Включены meta/storage/lifecycle/execution/API/bridge пакеты, не только feature/UI расширения. Новый candidate с тем же hostAbi можно опубликовать без restart. UI сохраняет mount identity и user-visible local state; backend удерживает pinned old generations. Никакие scopes, reservations или данные не сбрасываются ради reload.

Миграция состояния — явная чистая операция между точными TypeRef. Она создаёт проверенную новую ревизию и переключает указатель через CAS. Исходная ревизия сохраняется. Отсутствующий путь, неверный результат или конфликт не меняют исходные данные.

## Решение D08 — интерфейс как набор обычных плагинов

Web shell знает только загрузчик клиентских реализаций, общий error boundary и корневую mount point. Вкладки, маршруты предметных экранов, список проектов и сообщения определены UI-плагинами. Общий Inspector показывает только доступные поля схемы и сам поставляется стандартным плагином.

Кнопки и CLI ссылаются на один OperationRef. Транспорт возвращает receipt и даёт наблюдать исполнение. Состояние отображения не является состоянием работы. Для серверных изменений UI использует операции; прямой доступ к нормализованному общему store запрещён.

Проект/сессия/история/fork имеют свои схемы, операции, namespaces и views. Их отсутствие не ломает конфигурацию single-call. UI-слоты так же проверяются linker по точному контракту.

## Решение D09 — технический стек первой реализации

TypeScript strict; Node 24; npm workspaces; SQLite через better-sqlite3; JSON Schema draft 2020-12 через Ajv 8 (coerceTypes=false, useDefaults=false, removeAdditional=false); React 19 для web-представлений; Vite для dev shell; esbuild для plugin ESM bundles; node:test для backend contract suite; Playwright для браузерных acceptance.

A00 фиксирует точные patch-версии в package-lock.json и version manifest. Переход на другой стек требует решения, не допускается как удобство отдельного атома. Полный сервер первоначально один процесс и один writer. Конкурентные read/UI клиенты допустимы. Нельзя добавлять очередь, брокер, ORM, Kubernetes или распределённый scheduler для закрытия атомов v1.

Модули плагина разделены на shared/server/client. Server не импортирует React, client — Node builtins; это проверяет build. Клиентские ESM bundles используют host-provided React и SDK через import map, один экземпляр React на документ. Node entry загружается по проверенному локальному artifact path. Никакого eval серверных строк в браузере.

HTTP/stream transport работает на 127.0.0.1. В v1 нет удалённого multi-user доступа. Запросы изменения требуют локального bearer credential и допустимого Origin; credential не попадает в журналы, export и object inspector. Dev и packaged запуск используют одинаковые операции и storage adapter.

## Решение D10 — границы первой версии

Первая версия включает реальные плагины LLM, агентского цикла, детерминированных инструментов, памяти, проверок, истории, сессий, вкладок, проектов и fork устойчивой точки. У каждого есть минимальный работоспособный интерфейс/операции и тесты; общий framework без этих вертикальных сценариев не завершает задачу.

Внешний LLM подключается через один явно выбранный адаптер. Fake provider служит детерминированным тестам; финальная приёмка требует также одного реального вопроса–ответа при наличии настроенного провайдера. Если credential отсутствует, это блокирует только live-provider gate; fake-тесты не заменяют его.

После v1: недоверенные плагины в sandbox, multi-writer/distributed runtime, мобильные клиенты, marketplace, автоматическое слияние веток, live migration запущенных процессов, структурный subtyping и произвольные распределённые транзакции. API оставляет возможность этих расширений, но их код не входит в атомы v1.

## Рассмотренные альтернативы

| Вариант | Почему не выбран |
| --- | --- |
| Всё встроено в единый Agent/Session framework | Не выполняет REQ-03 и мешает новым предметным типам. |
| Произвольный JSON и глобальная event bus | Не определяет совместимость, порядок, владение, транзакции и восстановление. |
| Полностью самоизменяемое ядро | Не задаёт конечную bootstrap-точку и воспроизводимое значение операций. |
| Отдельная БД и сервис для каждого плагина | Усложняет atomic commit состояния/журнала/outbox без пользы первой версии. |

## Контрольная сборка

Один и тот же host загружает: single-call assembly; agent assembly с memory/tools/verify; workspace assembly с проектами/сессиями/вкладками; сторонний Checklist с операцией completeItem и собственным слотом item.badges; сторонний DueBadge в этом слоте. Ни одно подключение не требует предметных изменений host или web shell.
