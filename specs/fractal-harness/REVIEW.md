# Ревью концепции фрактального харнеса

Проверка трассировки AG-003: первоначальный HTTP adapter использовал внутренний `MODEL_CONFIGURATION_MISSING`. Исправлен на нормативный `DEPENDENCY_UNAVAILABLE` при отсутствии конфигурации/credential до transport. Если такой код возникает уже внутри transport, он не доказывает нулевой расход и остаётся unknown. Условия zero-call и conservative recovery не ослаблены; версии изменённых published packages увеличены, чтобы не переиспользовать package ID/version для новых байтов.

Уточнение реализации FH-15: статический effect export не мог получить scoped credential getter от native composition root. BOOTSTRAP.md дополнен необязательным `bindCapabilities` decorator при разрешении export для точного application instance. Публичные `EffectAdapter.execute/reconcile` и сохранённый EffectDefinition не меняются. Права и credential bindings проверяются для целевого instance, без чтения process.env внутри предметного плагина. AT-015 проверяет успешный вызов и ноль сетевых запросов при binding, выданном другому instance.

Уточнение реализации 2026-10-14: T4 требует в одном commit сохранить новую completion revision и ссылки Attempt.result/EffectResolution.result на неё. Изначальный ObjectStore выделял revision лишь после commit, поэтому такой batch было невозможно выразить. C05/RecordWrite дополнены необязательным заранее выделенным revision ID (непустая строка до 256 символов). Store проверяет отсутствие ID в истории до всех writes; тест AT-004 подтверждает идемпотентность и полный rollback при попытке повторного использования. Старые callers продолжают получать store-generated revisions. Разбиение T4 на два неатомарных commit не использовано.

**Статус: решения зафиксированы в спецификации; реализация ещё не проверена.**

Это ревью проектируемой системы и её контрактов. Оно не подтверждает работоспособность кода, прохождение тестов или готовность к эксплуатации. Каждый контрольный сценарий ниже необходимо реализовать и выполнить на соответствующем этапе плана.

Цель системы: любой компонент может быть заменён поддеревом с тем же внешним контрактом; плагины определяют собственные сущности, операции, состояние, хранение, интерфейс и слоты расширения. `Request`, `Invocation`, память, сессия, история, форк, вкладки и проект не являются предметными сущностями хоста.

Границы первой реализации зафиксированы: Node.js 24, TypeScript, доверенные плагины, React в браузере, один локальный SQLite store для транзакционных данных, точное совпадение `ContractRef`, неизменяемая сборка на время запуска. Поддержка недоверенного кода, распределённые транзакции и обновление работающего запуска находятся за пределами MVP.

Приоритеты: **P0** — нарушение делает архитектурные гарантии неверными либо создаёт риск потери/дублирования данных; **P1** — нарушение делает расширение и сопровождение неоднозначными. Принятые решения обязательны для реализации. Названия типов и точные формы данных задаёт [CONTRACTS.md](./CONTRACTS.md); очередность работ задаёт [PLAN.md](./PLAN.md).

## RV-01 — P0. Самоописание без конечного bootstrap

**Риск.** Если вся метамодель загружается произвольным плагином, возникает цикл: для чтения плагина уже нужно знать метамодель. Обратная ошибка — спрятать в хосте фиксированные сущности и назвать их техническими деталями. Тогда добавление нового вида работы снова потребует изменений ядра.

**Принятое решение.** Хост содержит только конечный bootstrap ABI: загрузку закреплённого пакета, вызов экспорта, передачу возможностей и общие примитивы хранения. Начальный bundle метамодели поставляется с закреплённым digest. Сначала проверяется его bootstrap-формат и целостность, затем регистрируются метаописания и проверяются их ссылки. Самоописание означает доступность описаний для той же системы типов и инспекции; оно не означает автоматическую замену семантики валидатора редактированием данных.

`Request`, `Invocation` и их переходы состояний объявляет стандартный плагин исполнения. Durable execution также реализуется стандартным плагином. `packages/host` не импортирует стандартные или прикладные плагины, не содержит их схем и не ветвится по их предметным состояниям. В частности, в хосте не появляются поля `session_id`, `request_id`, `project_id` и встроенное состояние «ожидание пользователя».

**Контрольные сценарии.**

- Запустить host без bootstrap bundle: получить явную диагностическую ошибку до активации прикладного кода и без создания скрытых предметных объектов.
- Изменить байт bundle, сохранив ожидаемый digest: загрузка отклоняется до исполнения экспорта.
- Проверить установленные метаописания публичным валидатором: все определения начального bundle валидны, ссылки разрешаются.
- Собрать host без пакетов сессии, проекта и исполнения: host остаётся собираемым; предметные возможности отсутствуют до установки соответствующих пакетов.
- Проверка зависимостей отклоняет импорт из `packages/host` в стандартный плагин или прикладной пакет.

## RV-02 — P0. Смешение определения, экземпляра и вызова

**Риск.** Одно слово «плагин» начинает означать пакет кода, описание типа, установленный компонент и конкретное выполнение. В результате два компонента неожиданно делят состояние, а перезапуск теряет идентичность.

**Принятое решение.** Различать поставляемый пакет, определения и экземпляры. `Type` описывает значение; `Contract` — операции и обязательства; `Implementation` — исполняемый экспорт, конфигурацию, состояние, слоты и требуемые возможности; `SlotDefinition` — место подключения; `Instance` — конкретный компонент; `Binding` — конкретное соединение. Эти конструкции представлены метаописаниями bootstrap bundle. Тип `Invocation` добавляет стандартный плагин исполнения.

Повторный вызов одного экземпляра не создаёт новый экземпляр. Два экземпляра одной реализации имеют разные идентификаторы и пространства состояния. Перемещение в композиции не меняет идентификатор. Путь в дереве используется для отображения и диагностики, а не как постоянный ключ хранения.

**Контрольные сценарии.**

- Создать два экземпляра памяти одной реализации; записать одинаковый ключ с разными значениями. Каждый читает только своё значение.
- Дважды выполнить один экземпляр: у вызовов разные идентификаторы, у владельца состояния — один прежний идентификатор.
- Переместить экземпляр в другой допустимый слот новой сборки: его идентификатор и namespace сохраняются, если операция явно сохраняет тот же экземпляр.
- Попытка сослаться на определение реализации как на экземпляр отклоняется при проверке сборки, до вызова кода.

## RV-03 — P0. Неопределённая совместимость контрактов

**Риск.** Автоматическое сопоставление «похожих» схем создаёт неявные преобразования, сложные правила подтипов и зависимость от порядка регистрации определений. Совпадение формы данных может ошибочно разрешить подключение семантически другого компонента.

**Принятое решение.** В MVP совместимость номинальная: слот требует точный `ContractRef`, реализация экспортирует тот же `ContractRef`. Версии фиксируются сборкой; диапазоны версий и `latest` не участвуют в выполнении. Для несовместимых версий нужен явный адаптер с собственным входным и выходным контрактом.

Схемы входа и выхода проверяются на границе вызова. Неизвестные поля, отсутствие обязательного поля, `null` и отсутствующее значение обрабатываются по явной схеме. Успешный результат с невалидной структурой превращается в ошибку контракта. Автоматического исправления, удаления полей или подстановки значений нет, если это не объявленная операция отдельного компонента.

**Контрольные сценарии.**

- Два контракта с одинаковой JSON-структурой, но разными `ContractRef` не соединяются.
- Реализация версии контракта 2 не подключается к слоту версии 1 без адаптера.
- Совместимый адаптер подключается и проходит проверки обеих границ; невалидный результат адаптера отклоняется.
- Невалидный вход не запускает реализацию. Невалидный выход не поступает родителю как успешный результат.
- Проверить отдельно отсутствующее поле, `null`, неизвестное поле и значение неверного типа: результат каждого случая соответствует схеме, а не coercion валидатора.

## RV-04 — P0. Типовая совместимость принята за поведенческую заменимость

**Риск.** Реализация может принимать и возвращать нужные данные, одновременно обходя обязательную проверку, увеличивая полномочия или производя запрещённый эффект. Типы не доказывают корректность поведения.

**Принятое решение.** Контракт сопровождается инвариантами и проверками соответствия. Поддерево экспортирует контракт через корневую реализацию. Права, лимиты и требования сборки проверяются независимо от заявления плагина. Потомок получает только явно делегированные возможности в пределах возможностей предка. Замена поддерева не отменяет обязательную проверку родителя.

В MVP плагины доверенные и исполняются в общем процессе. Ограничения API и проверки прав обеспечивают корректное использование контракта, но не являются изоляцией от злонамеренного TypeScript-кода, который способен обратиться к системным API. Спецификация не обещает такой защиты.

**Контрольные сценарии.**

- Через публичный API read-only компонента попытаться записать данные: операция отклоняется, ревизия и содержимое не меняются.
- Подключить поддерево с более широкими требованиями к возможностям: проверка сборки отклоняет его до исполнения.
- Заменить инструмент подагентом с тем же контрактом: обязательная проверка родителя всё ещё вызывается и может отклонить результат.
- Подагент с собственным лимитом не может превысить доступный остаток бюджета предка; отказ не создаёт незарезервированный внешний вызов.

## RV-05 — P0. Дерево владения смешано с графом ссылок

**Риск.** Общий backend или один дочерний компонент, прикреплённый в нескольких местах, делает удаление, остановку и владение состоянием неоднозначными. Цикл композиции может вызвать бесконечную активацию.

**Принятое решение.** Композиция экземпляров образует конечное дерево владения: у каждого некорневого экземпляра один владелец. Общие ресурсы подключаются через неприсваивающие владение ссылки или capabilities. Дерево UI и дерево исполнения могут иметь разную форму и ссылаться на одни объекты данных; эти ссылки не создают второго владельца экземпляра.

Области доступа и хранения задаются явно. Наличие ссылки на объект не предоставляет права его изменять. Удаление владельца не удаляет общий backend или чужие namespaces. Для операций с состоянием потомков используются объявленные контракты и делегированные возможности.

**Контрольные сценарии.**

- Подключение одного экземпляра в два owning-слота отклоняется.
- Цикл `A → B → A` отклоняется при проверке сборки; ни один узел не активируется.
- Два экземпляра используют один SQLite backend, но не читают чужие namespaces без предоставленного доступа.
- Удаление одного экземпляра сохраняет данные другого и доступность общего backend.
- Два представления одного объекта показывают одну его ревизию; закрытие одного представления не удаляет объект и не меняет дерево владения исполнения.

## RV-06 — P1. Порядок расширений определяет поведение неявно

**Риск.** Порядок загрузки пакетов неожиданно определяет последовательность проверок, выбор инструмента или результат интерфейса. Поведение одной сборки меняется между запусками.

**Принятое решение.** Слот явно задаёт контракт, кардинальность и форму подключения: одиночный элемент, упорядоченная коллекция либо коллекция по уникальному ключу. Позиции и ключи хранятся в сборке. Проверяются обязательность, максимум элементов и уникальность.

Владелец слота определяет, когда и как вызывает детей. Стратегии «все проверки», «первый успех», «параллельно» и «выбор по имени» принадлежат логике конкретной реализации. Установка нового пакета сама по себе не подключает его к существующим экземплярам. Runtime не придумывает fallback для пустого слота.

**Контрольные сценарии.**

- Загрузить одинаковую сборку с двумя разными порядками регистрации пакетов: разрешённые привязки и порядок вызовов совпадают.
- Два одинаковых ключа инструмента отклоняются, без выбора «последний победил».
- Отсутствие обязательного ребёнка блокирует активацию; пустой необязательный слот валиден.
- В упорядоченном слоте перестановка записана явно и меняет только новую сборку.
- Добавление пакета в каталог не меняет поведение уже собранного дерева.

## RV-07 — P0. Неизменность определений и сборки не обеспечена

**Риск.** Один идентификатор пакета и версия начинают означать разный код. Работавший запуск после рестарта получает новую реализацию или новую схему под прежней ссылкой.

**Принятое решение.** Определения имеют глобально однозначные имена в namespace пакета. Разрешённые точные версии и digest закреплены в lock-описании сборки. Один идентификатор пакета с одной версией не может соответствовать двум различным содержимым. Сборка и её привязки неизменны в пределах работающего запуска.

Обновление создаёт новую сборку. В MVP работающий запуск не переводится на другую сборку автоматически. Схема данных, версия реализации и версия контракта фиксируются отдельно: изменение одного не подразумевает совместимость остальных.

**Контрольные сценарии.**

- Попытка зарегистрировать другую реализацию под тем же package ID и версией отклоняется, если digest отличается.
- После установки новой версии уже начатый запуск продолжает использовать прежний digest.
- Восстановление по lock-описанию при отсутствующем пакете явно отказывает, без подстановки новой версии.
- Два пакета с совпавшим локальным именем определения не конфликтуют, если их полные namespaces различаются.
- В сборке не остаётся неразрешённых диапазонов версий или символических ссылок `latest`.

## RV-08 — P0. Собственное хранение плагинов разрушает атомарность

**Риск.** Если каждый плагин пишет в произвольное хранилище напрямую, новое состояние шага может сохраниться без намерения внешнего действия либо наоборот. После падения невозможно надёжно продолжить выполнение.

**Принятое решение.** Плагин владеет схемой данных и своим namespace; физической транзакцией управляет общий storage-контракт. В MVP все durable-данные располагаются в одном локальном SQLite store. Стандартный плагин исполнения в одной транзакции сохраняет новое состояние, записи своего журнала и outbox намерений эффектов. Хост предоставляет общую транзакционную механику и не знает предметного смысла этих записей.

Запись использует проверку ожидаемой ревизии. Набор namespaces, доступных транзакции, ограничен выданными правами. Внешний HTTP-сервис, файловая система и отдельная БД не становятся участниками этой транзакции автоматически. Необъявленную атомарность между несколькими внешними системами обещать запрещено.

**Контрольные сценарии.**

- Внедрить падение до commit: нет ни нового состояния, ни записей журнала, ни effect intent.
- Внедрить падение после commit: все три части присутствуют, незавершённый эффект обнаруживается после рестарта.
- Два писателя используют одну исходную ревизию: только один commit успешен; второй получает конфликт, без частичных записей.
- Ошибка в последней записи транзакции откатывает все её записи.
- Попытка включить чужой namespace без разрешения отклоняется до публикации изменений.

## RV-09 — P0. Восстановление дублирует внешний эффект

**Риск.** После принятия запроса внешним сервисом процесс падает до локального подтверждения. Простое повторение outbox создаёт второй объект. Термин «durable» ошибочно трактуется как exactly-once для любого инструмента.

**Принятое решение.** До отправки эффект получает стабильный идентификатор. Адаптер объявляет допустимую стратегию повторения: операция чтения, idempotency key, сверка результата или отсутствие автоматического повтора. Неопределённый результат записывается как отдельный исход. Без защиты от дублирования или возможности сверки автоматический повтор запрещён.

Replay использует сохранённые результаты и не вызывает внешние адаптеры. Resume продолжает прежнее исполнение по его закреплённой сборке. Fork создаёт новое продолжение по контрактам подключённых компонентов и не является автоматическим откатом уже произведённых внешних действий.

**Контрольные сценарии.**

- Остановить процесс после создания внешнего объекта, до подтверждения в SQLite. При idempotency key восстановление получает прежний объект; количество созданных объектов равно одному.
- Для адаптера со сверкой восстановление обнаруживает прежний результат и не выполняет повторное создание.
- Для адаптера без защиты после того же падения повторного запроса нет; исполнение сообщает неопределённость, а не успех.
- Выполнить replay при инструменте, который считает все реальные обращения: счётчик равен нулю.
- Изменить запрос в экспериментальном продолжении: результат старого эффекта не подставляется как ответ на другой запрос.

## RV-10 — P0. Миграции изменяют историю и работающие запуски

**Риск.** Обновление собственного хранилища плагина делает прежние снимки нечитаемыми, оставляет частично обновлённые записи или меняет данные ветви, которую пользователь ожидал сохранить.

**Принятое решение.** Namespace и снимок фиксируют точную схему состояния. Миграция объявляет исходную и целевую версии, не производит внешних эффектов, проверяет результат целевой схемой и публикует его атомарно. Исходный снимок сохраняется. При ошибке текущая версия и исходные данные не меняются.

Миграция выполняется явно для подготовленного состояния; live upgrade работающего запуска в MVP отсутствует. Нет неявного downgrade, автоматического вывода миграции по похожести схем или изменения закреплённых снимков старых запусков. Если компонент не поддерживает необходимое восстановление или ветвление, сборка показывает ограничение и отклоняет требующую его операцию.

**Контрольные сценарии.**

- Миграция возвращает невалидные данные: целевая версия не публикуется, исходные данные и ревизия сохраняются.
- Падение между вычислением и публикацией результата не оставляет частично мигрированного namespace.
- Отсутствует путь между точными версиями: обновление отклоняется до изменения данных.
- Успешная миграция нового продолжения не меняет снимок и сборку старого запуска.
- Попытка неявного downgrade отклоняется.
- Форк компонента без объявленного контракта ветвления получает явный отказ; универсальная копия его JSON не считается корректным форком.

## Условия завершения реализации

Ревью считается подтверждённым реализацией только после выполнения контрольных сценариев и соответствующих приёмочных тестов из плана. Одна успешная демонстрация LLM-вызова не подтверждает атомарность, восстановление, заменимость поддеревьев или независимость хоста от предметных сущностей.

Для приёмки должны существовать проверяемые результаты: вывод проверок архитектурных зависимостей, тесты несовместимых привязок, тесты с внедрением падений, подтверждение отсутствия повторных эффектов, проверка миграций и сквозной сценарий браузерного интерфейса. До получения этих результатов статус документа остаётся: **спецификация подготовлена; реализация не проверена**.
