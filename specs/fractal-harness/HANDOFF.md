# Инструкция исполнителю

Актуальное указание пользователя: сначала только [минимальный self-host](../../CURRENT-SCOPE.md). Не исполнять автоматически весь план. Остальные функции разрабатываются агентом через FRNESS по отдельным заданиям.

Выполняется самостоятельный продукт по этому пакету. Не начинать сразу с большого AgentManager или универсального UI-комбайна. Сначала прочитать README.md, ARCHITECTURE.md и нормативные контракты. Затем выбрать первый незавершённый атом из PLAN.md, у которого завершены зависимости.

## Порядок работы над атомом

1. Прочитать указанные в атоме разделы контрактов, файлы, его AT-сценарий из atomic-gates.json и общие инварианты. Поле plan.tests — трассировка полных требований; поэтапный gate задаёт именно AT, полный набор обязателен в FH-28.
2. Зафиксировать входное состояние: выполненные зависимости, доступные команды, текущие изменения.
3. Реализовать ровно заданные пути и поведение. Новый путь вне указанного диапазона допускается только для теста или очевидного внутреннего helper; изменение публичного контракта требует отдельного решения.
4. Запустить указанные проверки. Внешние эффекты тестировать fake-adapter, для crash tests использовать отдельный процесс remote fixture.
5. Выполнить локальный пользовательский сценарий атома. После появления UI проверить его в браузере, а не только typecheck.
6. Обновить implementation-status.json: status, evidence paths, команды и коды выхода. Поле done разрешено только при выполнении всего DoD.
7. Перейти к следующему разрешённому атому. Если есть реальный блокер, продолжить независимые атомы и записать точную причину.

## Запреты на упрощения

- Не заменять plugin-defined типы встроенными Agent/Session/Project классами в host.
- Не считать совпадение формы данных совместимостью разных ContractRef.
- Не выводить ID из пути дерева, названия вкладки или директории.
- Не исполнять plugin logic внутри SQLite-транзакции, если она может делать I/O; reducers допускают только чистые команды и storage batch.
- Не повторять unknown effect без стратегии из RUNTIME.md.
- Не считать replay повторным обращением к LLM или инструментам.
- Не закрывать задачу по тексту модели «готово»; только по проверке digest кандидата.
- Не освобождать неизвестный расход при cancel и не учитывать дочерний расход дважды.
- Не удалять данные вместе с отключением представления/плагина.
- Не делать тесты зелёными через skip, xfail, произвольные delays, снижение ожидаемых счётчиков или специальную ветку под scenario ID.
- Не менять acceptance tests одновременно с реализацией ради прохождения. Ошибка теста сначала оформляется отдельным изменением спецификации с объяснением.
- Не утверждать поддержку sandbox, exactly-once внешнего API или полной воспроизводимости живой модели.

## Адаптер исполняемых тестов

tests/acceptance.test.mjs вызывает интерфейс из acceptance-api.ts. Реализация адаптера располагается в packages/acceptance-adapter. Она преобразует данные в публичные API продукта и предоставляет тестовые clock/transport/crash hooks. В ней запрещены бизнес-логика, собственная БД, имитация registry/ledger и ответы по имени теста. Проверяемые функции обязаны выполняться в продукте.

## При остановке и передаче

Сохранить выбранный атом, проверенные файлы, результаты команд, неразрешённую ошибку и следующий конкретный шаг в implementation-status.json. Не менять source of truth на свободный чат. Отчёт «код написан» не равен «проверка пройдена».

Не делать commit/push/deploy автоматически по этому документу: текущая задача — подготовленный пакет реализации; дальнейший исполнитель следует актуальному поручению и правилам своего окружения.
